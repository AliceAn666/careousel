## Migration conflict: competing 0003 designs

Main and registration contain **0003_priority_scoring** (visitType, Intake, SymptomTag); batch contains **0003_notification_batches** (NotificationBatch, Offer.batchId, new constraints/trigger and replacement of the pending-offer index). They are different schemas. The checksum runner keys full directory names; equal numeric prefixes are not automatically a checksum collision, but sequence and assumptions are ambiguous, and merging both does not resolve their application semantics.

Preserve any applied SQL/name/checksum. First inspect the actual target migration ledger read-only. If batch migration has never been applied to the target, port it into a new reviewed next-unused additive migration (after registration 0004/0005, e.g. 0006, only after contract decision). If another environment already applied the batch 0003, keep that history intact and design an explicit convergence/forward migration with preflight; do not rename its applied directory or reset a database. Validate clean install and every known upgrade path on separate fixture databases. 0001/0002/0003_priority_scoring stay untouched. No competing migration is applied in Phase 1.
