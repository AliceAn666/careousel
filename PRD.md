## 2. Product and practical architecture

Careousel is an authorized cancellation-recovery network complementing clinics' existing scheduling processes. A patient manages multiple continuing care needs in one account. A clinic first offers suitable openings internally, then explicitly releases unused capacity to participating authorized clinics' patients. Staff control eligibility review, notification groups and scheduling decisions. Success is a durable, demonstrable recovery workflow; clinical benefit and commercial viability remain hypotheses.

Keep the existing Next.js App Router, React, strict TypeScript, original responsive CSS/Lucide, PostgreSQL, Prisma 6.19.2 with pg adapter, Zod, npm lockfile, Vitest and Playwright. Keep one application and one database. Do not migrate frameworks or restore the deleted static frontend. Persistent inbox and polling remain adequate for a short hackathon; no paid AI/API or message provider is needed. One PostgreSQL advisory lock is an acceptable demo throughput tradeoff. Thin route handlers, domain services and database constraints remain the boundaries.

Use integer cents with USD explicitly displayed, UTC persistence and clinic IANA timezone display. Current geography is one US metro with Pacific-time synthetic clinics. City/clinic selection is functional; distance routing/geocoding is deferred. Production accounts, EHR synchronization and real-time external hospital availability are not implemented.

## 4. Scheduling protection audit and integration risk

Current `performAction()` samples `new Date()` (or a test clock) inside the advisory-locked callback, before validation. This fixes the original pre-lock timestamp placement; it does **not** use PostgreSQL `clock_timestamp()`. The lock-wait regression advances an injected clock, not a real offer expiry observed by the database. Add a database clock sampled after lock acquisition (never transaction-start `now()`), plus real lock-wait tests for acceptance, direct booking and staff approval. Preserve lock 728194 and current timezone tests.

Remote cancellation commits before matching in a second locked transaction; the catch preserves cancellation and later reads retry derived suggestions. However, `getState()` still runs refreshMatches without an error boundary, so persistent matching failure can break the entire snapshot/UI. The injected failure occurs before refreshMatches rather than exercising an aborted SQL transaction. Test database failure, recoverable reads and explicit idempotent staff retry. Matching must never generate notifications automatically. Acceptance must remain one atomic transaction; do not apply cancellation's split-transaction pattern to replacement.

Current `0002` provides original Booking.replacementId→successor, patient-scoped composite foreign keys for Waitlist→Booking and Offer→Waitlist, plus a no-self/status check. Notification→Offer is not patient-scoped; slot status versus simultaneous booking/offer occupancy and raw-SQL patient overlap are not fully enforced by separate partial indexes. Add targeted SQL integrity tests and practical constraints only after data preflight.

Local-only review work uses the reverse `replacedBookingId` relation and different migrations named `0002_reschedule_history`/`0003_scheduling_integrity`; it also contains stronger SQL-clock, read-failure and integrity tests. **Do not combine these histories or apply both 0002 designs blindly.** T0 must reconcile useful behavior/tests onto the remote schema, preserve applied migration checksums and keep original local work untouched until separately reviewed. Remote VALIDATION reports its 0002 was applied in its environment; that does not establish which migrations exist on another teammate's machine.

Remote acceptance revokes all pending offers for a patient, including unrelated service needs. Multi-need support must revoke only same-need or genuinely conflicting offers, with concurrency tests. Existing service-string uniqueness must not be removed until stable need-level deduplication replaces it.

## 6. Backend transitions and scheduling contract

Occupancy and release phase are independent: Slot AVAILABLE/HELD/BOOKED continues to represent capacity; OpeningRelease INTERNAL_ONLY/EXTERNAL_REVIEW/NETWORK_OPEN/CLOSED represents audience permission. Patient search and **all direct-booking paths** must obey this audience gate, not merely the candidate list.

1. Cancellation transaction validates actor, changes booking to CANCELLED, releases occupancy, writes internal release deadline/policy snapshot and audit/event. If the cancellation itself fails, all these changes roll back and the UI reports failure. Once committed, matching failure cannot undo it; return matchingPending and offer safe retry. Ordinary new openings also begin internal-first unless the reviewed policy explicitly permits a different authorized path.
2. Derived matching checks active need/enrollment, internal relationship or active network memberships plus patient opt-in, service specification/duration, specific demo plan, target-clinic referral/auth validity, attendance lead time/preferences, price, earlier-only link and patient conflicts. Unknown required evidence means ineligible with a missing-information reason, not silent approval. Revalidate at invitation and acceptance.
3. Before internalUntil, only the clinic's own enrolled patients can receive offers. At/after deadline, INTERNAL_ONLY becomes EXTERNAL_REVIEW; deadline passage alone never authorizes external sharing. Staff explicitly releases to NETWORK_OPEN after confirming no successful internal fill, remaining holds resolved and permitted network. Membership/consent revocation invalidates affected pending network offers. An empty candidate set stays a visible no-match opening.
4. Clinician markers are pre-existing human inputs. Staff selects a qualified cohort, records rationale and approves its stage. Equal marker/cohort candidates use createdAt then stable ID. No click-speed clinical priority. Stages open no earlier than notBefore; later stages require staff authorization and cannot displace a live exclusive offer. Proposed safe first version is sequential exclusive offers inside a stage, not a race broadcast of multiple reservable invitations.
5. Staff offer approval atomically creates one PENDING offer, HELD slot and durable inbox entry/event. expiresAt=min(executionTime+clinic offer duration, slot.start−required arrival lead time); reject nonpositive remaining windows. Snapshot policy and eligibility versions; later changes cannot silently extend a hold.
6. Patient accept, under the same scheduling lock, obtains database execution time, revalidates ownership, unexpired state, release/network permission and all hard eligibility. In **one transaction**, create new confirmed booking, link and mark old RESCHEDULED, release old slot into its own internal process, fulfill only this need, revoke conflicting/same-need offers, confirm occupancy and persist notification/events. Failure rolls back everything and protects the old appointment. No external cancellation is claimed.
7. Decline/expiry releases a hold and preserves original booking and still-valid need. Repeated same response succeeds without duplicate events/notifications; contradictory response returns conflict. Expiry correctness must not require a worker or browser timer. Staff can retry matching explicitly; reads degrade safely if projection fails. Reopening/renotifying requires a deliberate new stage, not an accidental retry.

For a hackathon, lazy reconciliation under the lock plus UI polling is acceptable. Timed stages become eligible by server deadline and staff action; do not promise background delivery at an exact second. Durable stage/release rows allow restart recovery. A scheduler can be added later without changing rules.

## 8. Complete proposal-aligned demonstration and impact metrics

3. Staff reviews synthetic pre-screened internal candidates and existing clinician markers; opens the priority stage. The shown internal candidate declines or expires; no medical judgment is made by AI. Stage notices persist; there is only one actionable hold per slot.
4. After the configurable internal window, staff explicitly authorizes network release. 6. Avery accepts. New Cedar booking and Harbor reschedule/history commit atomically; Harbor receives its own internal opening. Refresh/restart preserves the result and Avery's independent need. Concurrent or expired acceptance safely fails without losing Harbor.
7. Clinic Impact shows the observed recovered opening and time-to-fill, earlier days and internal vs network attribution. Simulation inputs demonstrate economics without claiming observed profit or measured staff time savings.
8. Show no-match, repeated decline, expired-offer and unauthorized-release cases using deterministic fixtures. No real integrations, insurer calls or payments are involved.

Metric definitions: eligible cancelled openings are the denominator; confirmed recovered openings count once per release, excluding ordinary new bookings and duplicate events. Show internal and network recovery separately, reversals/re-cancellations and current recovered status. Observed time-to-fill = confirmation time minus cancellation release time; earlier days = floor((original.start−replacement.start)/86400000), disclose elapsed-day convention. Incremental recovery beyond existing clinic systems is **not causally measurable in this local demo**: show observed network recoveries as a proxy and a separately labeled hypothetical baseline comparison. Completed visits/no-shows require synthetic outcome flags and cannot be inferred from confirmation. Administrative effort is a labeled scenario estimate from configurable minutes per task unless directly measured; no invented actual staff savings.

Financial scenario: incremental contribution per completed visit × assumed additional completed visits − subscription/usage scenario fee − additional integration/admin costs; platform contribution also deducts its own hypothetical costs. $20/use, $250/month and the 13-use comparison are proposal examples with comparable-scope caveat. No charge is collected; patient Careousel booking fee is always $0, medical-service estimate remains separate. Never promise cheaper medical bills, proved ROI or novel/unique competitor capabilities. Real transaction-based billing requires legal review and separate authorization.
